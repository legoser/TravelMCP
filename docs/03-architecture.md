# 03. Архитектура

Компонентная архитектура `travelmcp`. Слой за слоем: интерфейс → ядро → данные → наблюдаемость.

## Общая схема

```
[ИИ-агент / MCP-клиент]
        │  MCP (Streamable HTTP, stateless, JSON-RPC)
        ▼
┌───────────────────────────────────────┐
│  cmd/mcp-server — точка входа          │
│  mcp-go-обвязка + go-sdk              │
│    Tools / Resources                  │
└───────────────┬───────────────────────┘
                │
┌───────────────▼───────────────────────┐
│  internal/app — оркестрация            │
│  auth (API-ключ) → usecase (найти      │
│  маршрут) → planner → adapters         │
└───────────────┬───────────────────────┘
                │
       ┌────────┼────────────┬─────────────┐
       ▼        ▼            ▼             ▼
┌──────────┐ ┌──────────┐ ┌───────────┐ ┌──────────────┐
│ planner  │ │ config   │ │ telemetry │ │ adminrest    │
│ (ядро    │ │(dynamic, │ │(otel,     │ │ (REST + веб- │
│  CSA/    │ │ hot-     │ │ prom,     │ │  страница)   │
│  RAPTOR, │ │ reload)  │ │ health)   │ │              │
│  transfers,gap) │         │           │              │
└──────────┘ └──────────┘ └───────────┘ └──────────────┘
       │
       └── providers (адаптеры источников)
           synth │ gtfs │ govregistry │ osm │ scraper*
               └──────────────┼───────────────────┘
                              ▼
                 хранилище: PostgreSQL + PostGIS
        (пользователи, ключи, конфиг, кэш расписаний,
         счётчики метрик; spatial-индексы ближайших остановок)
```

## Компоненты

### 1. `internal/model` — каноническая модель данных

Единственная модель, с которой работает ядро. Адаптеры приводят к ней данные источников.

```go
Stop     // остановка/платформа: id, координаты (lat/lon), name, ref (id источника)
Route    // маршрут/линия: id, short_name, long_name, mode (bus, tram, rail...), provider
Trip     // рейс: маршрут + дни действия + направление
StopTime // привязка рейса к остановке: время прибытия/отправления, порядковый номер
Connection  // соединение (CSA): from StopTime -> to StopTime, время, trip
Transfer    // пешая стыковка между остановками: from, to, walk_time
Leg      // итоговый этап маршрута: mode, from/to (stop или точка), время, trip, provider
Journey  // итог: []Leg + суммарное время + пересадки + cost (поле-шов)
Cost     // расширяемое поле: amount, currency, basis (estimate|fare), method — будущий cost-движок
```

Ключевые свойства модели:

- **Provider-affinity**: каждый объект помнит источник (`provider_id`). Это нужно для метрик (вклад провайдера), стыковок и честной обработки «белых пятен».
- **Открыта для расширения**: `Leg` несёт `Cost`; добавление тарифов не ломает модель.
- **«Белое пятно» как leg**: разрыв покрытия — тоже `Leg` с `Mode: self_walk/self_taxi/self_car`, помечается как участок ответственности пользователя.

### 2. `internal/providers` — реестр адаптеров

Каждый источник — пакет с единым интерфейсом:

```go
type Provider interface {
    ID() string
    Health() HealthStatus   // up/down, свежесть, остаток лимитов
    // построение/обновление локальных данных под каноническую модель
    Load(ctx) error         // импорт данных (GTFS, реестровый CSV) или
    // для REST-провайдеров:
    Query(journeyRequest) ([]Leg, error)
}
```

Реестр (`registry`) собирает провайдеров по конфигурации (список в динамическом конфиге), проверяет здоровье каждого, оборачивает вызовы телеметрией. Провайдеры первой волны:

- `synth` — синтетический мок (не продакшн-источник; только для тестов/демо,
  включается явно через `PROVIDERS_ENABLED=synth` — по умолчанию выключен);
- `gtfs` — импорт GTFS-фидов (Москва, СПб), разбор CSV в каноническую модель, кэш в БД;
- `govregistry` — реестры Минтранса РФ (межрегиональные маршруты, остановочные пункты, тарифы) — CSV;
- `osm` — остановки и пешеходная сеть из OSM (не провайдер маршрутов, а источник геометрии/точек);
- `scraper` — (позже, точечно) сайты перевозчиков; при обязательном наличии метрик здоровья и валидатора.

### 3. `internal/geo` — пространственные задачи

- поиск ближайшей остановки к точке (`nearest stop`);
- построение пеших стыковок между остановками/хабами;
- расстояние и время пешей доступности (Access/Egress leg'и);
- геокодирование входных точек (адрес → координаты) — внешний сервис-адаптер.

Реализация: PostGIS-запросы (индексы) + in-memory-индекс H3/S2 для горячей части.

### 4. `internal/planner` — ядро планирования

Порядок построения маршрута:

1. **Pre-query**: геокодинг точек → nearest stop (из координат «активации» на ближайшие остановки/вокзалы).
2. **Traversal**: трансфер-граф из канонической модели (соединения + пешие стыковки).
3. **Algorithm**: CSA (первый этап) → RAPTOR multi-criteria (дальше). Учитывает настройки пользователя (max transfers, allowed modes, max walk, arrival-by/departure-at).
4. **Gap-detection**: там, где между узлами цепочки нет покрытия, вставляет `self-leg`.
5. **Assembly**: собирает `Journey` (access → транзит → → egress), валидирует стыковки, отдаёт в usecase.

Требования к данным ядра: координаты; минимальные времена пересадок; пешие дистанции между стыковочными остановками; расписания в нормализованной памяти (или parquet-кэш) — миллионы соединений за миллисекунды.

### 5. `internal/config` — динамическая конфигурация

- Три уровня: env (секреты/адреса) → YAML-файл (`configs/config.example.yaml`) → база данных.
- Hot-reload: изменения, внесённые через REST админки (источники, feature-флаги, дефолты) применяются без перезапуска.
- Per-user настройки поиска: хранятся в БД, переопределяют дефолты при выполнении запроса.

### 6. `internal/auth` — идентификация и права

- API-ключи со скоупами для MCP/REST (stateless, из заголовков).
- Модель пользователей: саморегистрация → статус `pending` → модератор подтверждает/отклоняет.
- JWT-сессии для админки.

### 7. `internal/adminrest` — REST API и минимальная веб-страница

Эндпоинты:
- `/api/v1/users`, `/api/v1/users/{id}/moderate` — регистрация и модерация;
- `/api/v1/keys` — управление API-ключами;
- `/api/v1/providers` — управление источниками, статусы, запуск импорта;
- `/api/v1/config` — просмотр/изменение динамического конфига;
- `/api/v1/dashboard` — агрегаты для дашборда (здоровье компонентов, нагрузка, внешние запросы);
- `/healthz`, `/readyz` — health-эндпоинты.

Минимальная веб-страница (шаблонизируемая): логин, таблица пользователей с модерацией, список источников, дашборд.

### 8. `internal/telemetry` — наблюдаемость

- **Health**: `/healthz` (жив), `/readyz` (готов: БД, кэш, реестр провайдеров).
- **Метрики** (OpenTelemetry → Prometheus):
  - сервисные: RPS, латентность p50/p95, error rate, активные пользователи;
  - по провайдерам: up/down, латентность, error rate, **остаток лимитов/квоты**, **freshness** (возраст последнего успешного импорта);
  - скрейперов: число успешных страниц, обрывов селекторов (сигнал «сайт изменился»);
  - планировщика: построено маршрутов, число маршрутов по провайдерам, доля self-leg.
- **Логи**: структурированный JSON, request-id в контексте.
- **Трейсы**: провайдерские вызовы (таймауты, ретраи).
- **Grafana**: дашборды; агрегаты для встроенной админской панели — из БД-счётчиков или PromQL.

## Общие правила

- Адаптеры **никогда** не вызывают ядро — только наоборот. От падения/деградации одного провайдера сервис не падает: таймауты, ретраи, метрики, понятная ошибка в ответе.
- Все внешние вызовы — через единый HTTP-слой с телеметрией.
- Секреты и ключи — только через env; в репозиторий не попадают.
- Каноническая модель и протокол обмена с ИИ-агентом (MCP) стабильны; внутренние реализации меняются свободно.
