# 02. Словарь терминов и технологий

Словарь для проекта `travelmcp`. Группировка по разделам; термины иностранные, пояснения — на русском.

## A. Понятия маршрутизации и поездки

| Термин | Пояснение |
|---|---|
| **Itinerary / Journey** | Итог поиска: полная цепочка «дверь-в-дверь» от А до В со всеми этапами и временами. |
| **Leg (этап / плечо)** | Одна поездка без пересадок: сел в транспорт маршрута N в точке X, вышел в точке Y. Базовая единица нашего ядра. |
| **Segment** | Участок пути; в нашем случае совпадает с leg. |
| **Transfer (пересадка / стыковка)** | Переход между leg'ами. Стыковка корректна, если `прибытие + минимальное время пересадки <= отправление следующего leg'а`. |
| **Connection (соединение)** | Элементарная запись расписания: рейс из стопа A в стоп B в заданное время. Единица алгоритма CSA. |
| **Access leg / Egress leg** | Пешие (или иные) этапы «от адреса до первой остановки» и «от последней остановки до адреса». |
| **Nearest stop search** | Поиск ближайшей к точке остановки/платформы (через пространственный индекс PostGIS/H3). |
| **Gap (разрыв покрытия)** | Сегмент маршрута без цифровизованного сообщения общественного транспорта; закрывается self-leg'ом. |
| **Self-leg (самостоятельный участок)** | «Своими силами»: пешком, вело, такси, личный автомобиль. В нашем UI/ответе — «ответственность пользователя за участок». |
| **Arrival-by / Departure-at** | Режимы поиска: «прибыть к времени T» или «отправиться после времени T». |
| **Time window** | Окно отправления: несколько вариантов в заданном диапазоне времени. |
| **Minimum transfer time** | Минимальное время пересадки между остановками (время, нужное, чтобы покинуть одно ТС и сесть в другое). |
| **Interlining** | Продолжение рейса «в одном транспортном средстве» (идентификатор рейса меняется, транспорт тот же) — это НЕ пересадка, пассажир остаётся в ТС. |
| **Multi-criteria / Pareto** | Оптимизация по нескольким целям одновременно (время, число пересадок, стоимость): результат — набор «лучших недоминируемых» вариантов (Парето-фронт), а не один «оптимальный». |
| **Isochrone** | Изохрона: зона достижимости из точки за время T. |
| **Footpath** | Пеший путь между остановками (в GTFS описывается в `transfers.txt`). |
| **Coverage (покрытие)** | Какие населённые пункты/направления имеют машиночитаемые расписания. |

## B. GTFS — язык расписаний

**GTFS (General Transit Feed Specification)** — открытый стандарт представления расписаний общественного транспорта. Набор текстовых CSV-файлов в ZIP-архиве.

| Файл | Содержимое |
|---|---|
| `agency.txt` | Перевозчики. |
| `stops.txt` | Остановки/платформы с координатами и названиями. |
| `routes.txt` | Маршруты (линии). |
| `trips.txt` | Конкретные рейсы (экземпляры маршрута на дату/день недели). |
| `stop_times.txt` | Привязка рейсов к остановкам с временами прибытия/отправления и порядковым номером. |
| `calendar.txt` / `calendar_dates.txt` | Дни действия сервиса (ранговые дни недели / отдельные даты). |
| `frequencies.txt` | Интервалы движения (для высокочастотных линий) в дополнение к точным временам. |
| `shapes.txt` | Геометрия маршрута (полилиния). |
| `transfers.txt` | Правила пересадок (в т.ч. footpath между остановками). |
| `fare_attributes.txt` / `fare_rules.txt` | Тарифы и правила их применения (для будущего cost-движка). |
| `feed_info.txt` | Метаданные фида. |

Дополнения:
- **GTFS-RT** — realtime-дополнение: TripUpdates (задержки/отмены), VehiclePositions (положение ТС), ServiceAlerts (алерты). На первом этапе не используем.
- **GTFS-Flex** — гибкие маршруты «по требованию».
- **Mobility Database** — каталог мировых GTFS-фидов (например, фид Москвы `mdb-3226`).
- **GTFS Validator** (MobilityData) — инструмент проверки качества фидов.

## C. Другие форматы и стандарты данных

- **NeTEx** — европейский стандарт обмена расписаниями (XML), поддержан в OTP2.
- **SIRI** — европейский стандарт realtime-информации.
- **HAFAS** — проприетарный формат расписаний компании HaCon (используется Deutsche Bahn и др.), а также формат многих европейских планировщиков.
- **OSM public_transport** — схема тегов в OpenStreetMap: `stop_position`, `platform`, `route`, `route_master` — картографический скелет остановок и линий (те же остановки, но без расписаний).
- **Открытые данные (Open data)** — данные, публикуемые для свободного использования; в проекте: реестры Минтранса РФ в формате CSV.

## D. Алгоритмы маршрутизации

- **CSA (Connection Scan Algorithm)** — «скан соединений»: весь набор соединений сортируется по времени, один проход отвечает на запрос «прибыть раньше всего». Простота реализации, миллионы соединений обрабатываются за миллисекунды. Первый кандидат для ядра.
- **RAPTOR (Round-based)** — поиск «раундами пересадок» (раунд 1 — первый транспорт, раунд 2 — первая пересадка и т.д.). Легко расширяется на многокритериальную оптимизацию и настройки пользователя. Следующая ступень ядра.
- **Trip-based** — поиск по «трипам» (рейсам), один из самых быстрых, но и самый сложный в реализации.
- **Transfer Patterns** — построение «шаблонов пересадок» для очень больших статичных сетей.
- **Готовые движки** (не ядро, возможные будущие адаптеры):
  - **OTP2 (OpenTripPlanner 2)** — Java, GTFS + OSM, мощный и тяжёлый;
  - **MOTIS** — C++, очень быстрый, сложный деплой;
  - **Valhalla / OSRM / GraphHopper** — дорожные движки (полезны для расчёта самост. участков: пешком/авто).

## E. Геоданные

- **PostGIS** — пространственное расширение PostgreSQL: индексы и запросы для «ближайших соседей», буферов, пеших дистанций.
- **H3 / S2** — геометрические сетки-индексы для быстрого поиска ближайших точек на сфере.
- **Overpass API** — точечные запросы к данным OpenStreetMap.
- **Geofabrik** — региональные выгрузки OSM (файлы `.osm.pbf`).
- **Геокодинг / Reverse geocoding** — преобразование «адрес ↔ координаты» (в т.ч. для входных точек MCP-запроса).

## F. Инфраструктура и стек

- **MCP (Model Context Protocol)** — открытый протокол интеграции ИИ-агентов с инструментами и данными. Основные сущности: **Tools** (инструменты), **Resources** (ресурсы), **Prompts** (шаблоны промптов). Транспорты: **stdio** (локально) и **Streamable HTTP** (удалённо; стандарт на 2026, SSE устаревает). Спецификация **2026-07-28** сделала протокол stateless.
- **JSON-RPC** — формат сообщений MCP.
- **`modelcontextprotocol/go-sdk`** — официальный Go SDK для MCP (типизированные тулы, генерация JSON Schema из Go-структур; коллаборация с Google; спецификация stateless).
- **`mark3labs/mcp-go`** — community-библиотека MCP для Go; удобный HTTP/SSE-транспорт.
- **Mobroute** — библиотека/CLI на Go: CSA-роутер по GTFS, самостоятельная загрузка фидов из Mobility Database в SQLite. Референс реализации CSA на Go; потенциальный готовый блок для внутреннего расписания города.
- **OpenTelemetry** — стандарт для метрик, трейсов и логов.
- **Prometheus / Grafana** — сбор метрик и дашборды.
- **Health-эндпоинты** — `/healthz` (жив ли процесс) и `/readyz` (готов ли обслуживать: БД, кэш и т.д.).

## G. Специфика России и СНГ

- **Реестр межрегиональных автобусных маршрутов (Минтранс РФ)** — открытые наборы CSV: действующие маршруты, остановочные пункты, тарифы, отменённые и международные маршруты. Открытая лицензия, коммерческое использование разрешено. Важно: почасовых расписаний в этих наборах нет — есть структура маршрута и частоты отправлений.
- **Региональные порталы открытых данных** — разрозненные расписания в CSV/JSON/HTML (data.gov.ru и региональные сайты).
- **Яндекс Расписания** (`api.rasp.yandex.net`) — расписания поездов/автобусов по РФ; исторически бесплатный доступ по ключу; домен может быть недоступен из-за внешних условий → адаптер должен это переживать.
- **2ГИС / Яндекс Карты API** — коммерческие тарифы, условия лицензий запрещают хранение и перепродажу данных; на старте не используются.
- **Скрейпинг (парсинг страниц)** — хрупкость: селекторы «ломаются за ночь»; антибот-защита; неопределённость по условия сайтов; риск «200 OK с неверными данными». Поэтому: точечно, модульно, с валидацией данных и метриками здоровья.
- **152-ФЗ** — закон о персональных данных; учитывается при работе с учётными записями пользователей и логированием.

## H. Доменные термины «для пользователя проекта»

- **Цифровизованное сообщение** — наличие машиночитаемых расписаний для населённого пункта/направления.
- **Ответственность пользователя за участок (self-leg)** — сегмент маршрута, который нужно преодолеть самостоятельно (пешком/вело/такси/авто); помечается в маршруте явно.
- **Стыковка (connection)** — согласование по времени между разными рейсами/видами транспорта.
- **Мультимодальность** — использование нескольких видов транспорта в одной цепочке.
- **MaaS (Mobility-as-a-Service)** — подход «мобильность как сервис», интеграция разных видов транспорта в одном планировщике; проект — минимальная его реализация.
- **Агрегатор расписаний** — система, собирающая расписания из многих источников в единую модель.
