# 04. Источники данных

Реестр источников, стратегия подключения и требования к каждому. Общий принцип: **все адаптеры приводят данные к канонической модели** (см. `03-architecture.md`), ядро от источника не зависит.

## Классификация источников

| Тип | Формат | Покрытие РФ/СНГ | Легальность/стабильность | Затраты адаптера |
|---|---|---|---|---|
| **GTFS-ленты** | ZIP/CSV, стандарт отрасли: остановки, расписания, геометрия, тарифы | Москва (MobilityDatabase `mdb-3226`), СПб (static + realtime API), часть регионов | Открытый стандарт; стабильно; следить за обновлениями фидов | Низкие |
| **Реестры Минтранса РФ** | CSV: межрегиональные маршруты, остановочные пункты, тарифы, отмены | Межрегиональные автобусные маршруты по всей РФ | Открытая лицензия, коммерческое использование разрешено | Низкие |
| **OpenStreetMap** | OSM: остановки, маршруты-линии, пешеходная сеть | практически вся РФ/СНГ (точность хуже в провинции) | ODbL, стабильно | Средние |
| **Яндекс Расписания** (опционально) | REST JSON | широкое по РФ | Бесплатный по ключу исторически; домен может быть недоступен из-за внешних условий; лицензия запрещает хранение/перепродажу | Средние |
| **Сайты перевозчиков** (скрейпинг, позже) | HTML/PDF/картинки | точечно | Серая зона: хрупкость, антиботы, ToS; каждый сайт = свой скрейпер + сопровождение | Высокие на сопровождение |
| **Синтетика** | собственный тестовый набор | — | — | Минимальные |

## Стратегия первой волны (без платных API)

Порядок подключения — от наибольшей ценности/наименьшей стоимости:

1. **Синтетика** — всегда доступна; разработка и тесты ядра без внешних зависимостей.
2. **Реестр Минтранса РФ** — покрывает межрегиональные автобусные маршруты (самый дефицитный сегмент); даёт связность «город → город».
3. **GTFS Москвы и СПб** — почасовые расписания внутри крупных городов (access/egress, городские пересадки).
4. **OSM** — остановки и пешеходная сеть: ближайшие точки посадки/высадки, пешие стыковки между хабами.
5. **Яндекс Расписания** — опционально, если понадобятся почасовые межрегион расписания.

Скрейпинг — **отложен**: подключается точечно под конкретный целевой город, строго с метриками здоровья и валидацией данных.

## По источникам

### GTFS (Москва, СПб, далее — другие фиды)

- **Что берём**: `stops`, `routes`, `trips`, `stop_times`, `calendar`, `calendar_dates`, `shapes`, `transfers` (при наличии), `fare_attributes`/`fare_rules` (в будущее, cost-движок).
- **Куда**: нормализуем в каноническую модель → кэш в PostgreSQL (+ parquet для больших расписаний).
- **Периодичность**: по расписанию фидов (обычно еженедельно/при изменении, по `feed_info`/дате файла).
- **Метрики**: возраст последнего успешного импорта (freshness), число трипов/стопов, ошибки валидации.
- **Провайдер-ссылки**: единый `provider_id` на фид; несколько фидов — несколько провайдеров.

### Реестры Минтранса РФ

- **Наборы**: «Реестр регулярных автобусных маршрутов между субъектами РФ», «Реестр остановочных пунктов по межрегиональным маршрутам», «Перечень услуг и тарифов для остановочных пунктов», «Количество отправлений», отменённые и международные маршруты.
- **Форматы**: CSV, обновляется регулярно (реестры актуальны, например, на 19.08.2026).
- **Что важно знать**: почасовых расписаний нет — есть структура маршрута и частоты. Значит:
  - используем для построения связности, стыковок между городами и «коридоров» маршрутов;
  - точные времена берём оттуда, где есть (GTFS, скрейпинг перевозчика), а реестр — как каркас и источник правдивости «есть/нет сообщения».
- **Метрики**: количество маршрутов/остановок, дата реестра, ошибки разбора.

### OSM

- **Что берём**: `public_transport=platform/stop_position`, маршруты (`route`, `route_master`), пешеходная сеть (`highway=pedestrian/footway/...`).
- **Как**: Geofabrik-выгрузки регионов или точечные запросы Overpass. Парсеры: `prism` (OSM→GTFS), `osmptparser` (Rust/Py).
- **Зачем**: nearest stop по координатам, пешие стыковки, access/egress leg'и, определение «достающего хаба».
- **Важно**: OSM — без расписаний; только геометрия. Не источник маршрутов с временами.

### Скрейпинг сайтов перевозчиков (будущее, точечно)

- **Когда**: после того, как ядро и метрики работают; под конкретный целевой город/перевозчика, где нет других данных.
- **Требования**:
  - модульный скрейпер на тот же интерфейс Provider;
  - нормализатор «сырой HTML → каноническая модель»;
  - валидатор данных (контроль количества полей, диапазонов, свежести);
  - метрики здоровья (обрывы селекторов = алерт «сайт изменился»);
  - уважение rate-limit и robots.txt; осознаёт риски ToS.
- **Оценка**: 1–2 дня на первый сайт + постоянное сопровождение.

### Платные API (Yandex Maps, 2ГИС и др.)

На первом этапе **не используются**: коммерческие тарифы и лицензии, запрещающие хранение/перепродажу. Архитектура допускает добавление REST-провайдера позже без изменений ядра.

## Метрики здоровья по каждому источнику

| Метрика | Пояснение |
|---|---|
| `provider_up` | Доступен ли источник (сеть/API/файл). |
| `provider_latency` | Время запроса/обработки. |
| `provider_errors` | Ошибки (с кодами). |
| `provider_quota_remaining` | Остаток лимитов (для API с квотами). |
| `provider_freshness` | Возраст последних успешно импортированных данных. |
| `provider_import_ok` | Успешность последнего импорта; число записей. |
| `scraper_selector_breaks` | (для скрейперов) обрывы селекторов/изменение разметки. |
