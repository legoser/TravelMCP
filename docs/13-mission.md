# 13. Миссия

## 1. Цель

Построить полноценную базу данных междугородного и регионального общественного транспорта России с верифицированными геоданными, из которой строится мультимодальный маршрут «дверь-дверь» и экспортируется единый `gtfs.zip` на всю страну.

## 2. Принципы

* **Качество данных выше покрытия.** Координата, имя, связь — только после перекрёстной проверки независимыми источниками. `MOTIS` geocoder построен на `OSM` — это один источник `A=OSM/MOTIS`, независимыми являются `B=Минтранс`, `C=Яндекс Расписание`, `D=Nominatim/OpenAddresses`. Верифицированным считается объект с `confidence ≥0.6` (`<500м` + `lev<len0.15`; сильный одиночный матч `B`/`C` с `<200м`+`lev==0` уже даёт `0.6` — см. `14-plan.md:3.8`); иначе попадает в `review_queue`. Пороги калибруются до Фазы 1 на данных Кузбасса, хранятся в `config verification.*` без пересборки. Ложные данные не попадают в прод.
* **Одна истина.** `PostgreSQL + PostGIS` — единственный прод-стор. Очищенные подготовленные данные хранятся только в БД. `json` — только для моков тестов (`synth`). Историчность — SCD2 `valid_from/valid_to` на `places/terminals/routes` (см. `14-plan.md:3.9`), стабильные ID (`never reuse`, `feed_info.feed_version`) и `WAL/PITR` — обязательны для масштаба.
* **Плагин-коннекторы.** Каждый источник — коннектор с жизненным циклом (сбор → адаптация → верификация → импорт → обновление). Логика импорта — внутри приложения, управляется из админки.
* **Двуязычие по стандарту.** `ru` — прод, `en` — международный доступ. Собственные имена — транслит по `ГОСТ 7.79 / ISO 9`, нарицательные — перевод по `ISO 3166-2` / `UNGEGN` (`область→Oblast`, `район→District`, `городской округ→Urban Okrug`). Хранение `ru`+`en` параллельно.
* **GTFS — продукт.** Один `gtfs.zip` на РФ компилируется из БД и отдаётся наружу; не источник, кроме внешних GTFS-фидов (Москва/СПб) как входящих коннекторов (все фиды проходят `AdaptedRecord → верификация → канон`, pass-through запрещён). `gtfs.zip` — мульти-агентный по `carriers` (`agency_id = carriers.id`), `feed_info.feed_version` стабилен, разведён `provider` vs `carrier` — см. `14-plan.md:3.6,3.9`.

## 3. Границы

* **Делаем:** терминалы, остановки, маршруты, рейсы, расписания (календарь), пересадки, цены, зоны, иерархия мест, связи.
* **Не делаем сейчас:** уличный роутер (бэклог, `MOTIS` покрывает), продажа билетов, realtime `GTFS-RT`, платные API без свободного доступа.
* **Стек:** `Go` (`travelmcp`), `MOTIS v2.11` (`api.transitous.org`, `192.168.57.14:8077` локально), `PostgreSQL+PostGIS`, `Docker Compose`.

## 4. Источники

* `MOTIS` (вся Россия загружена) + `OSM` — гео-верификатор, иерархия `admin_level` (`/api/v1/geocode`, `/api/v1/reverse-geocode`, `/api/v6/map/stops`).
* Реестр Минтранса РФ (`XLSX` 5 листов, `~5600` маршрутов) — каркас связей.
* `Яндекс Расписание` — расписания/цены, пополняемый сборщик с квотами (`api_quotas` `PK(provider,day)`, атомарный `ON CONFLICT WHERE used<limit`).
* Внешние `GTFS` (Москва `mdb-3226`, СПб) — входящие фиды через коннектор.
* Адресные данные — свободный `Nominatim` / `OpenAddresses` для сверки (временно API).

## 5. Критерии готовности

* БД содержит все города Кузбасса и Томской области с корректными координатами, `ru`+`en` именами, связями `place_closure` (консистентность `closure` vs `parent_id` проверена ночным job'ом), сезонностью; скоп пилота — Кузбасс/Томская, РФ целиком — отдельная Фаза 6 вне 29-дневного плана (`14-plan.md:2`).
* Сборщик `Яндекс` работает с учётом квот в БД (атомарный `UPDATE ... WHERE used < limit RETURNING`, строка на день `PK(provider,day)`, `reset_at` 00:00 MSK), перезапуск не теряет счётчик.
* Админка с аутентификацией и `audit_log` позволяет запустить импорт, вызвать внешний API, провалидировать, сохранить ручную правку (`provenance.actor_id` фиксирует оператора).
* `gtfs.zip` (один, мульти-агентный по `carriers` без префикса `provider:`) проходит `gtfs-validator` и импортируется в `MOTIS` для `GET /api/v6/plan`; `shapes.txt` отсутствует осознанно в MVP, `pickup_type/drop_off_type` заложены в схеме.
